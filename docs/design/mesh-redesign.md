# gst 重新设计：分层的 mesh 与成员

> 这是本版重构的方案记录。实现之后的协议和术语以 `mesh.md` 和 `AGENTS.md` 为准：`network` 条目改叫 `subnet`，`member` 字段改叫 `membership`，`mesh.nodes` 改叫 `mesh.topology`，`edges` 改叫 `links`，`path` 改叫 `route` 或 `way`，`net.networks` 改叫 `net.prefixes`，“成员”统一说成“在网络里的 node”。

状态：已实现（协议 6），规格已合并进 `mesh.md`，以那份为准；本文保留作评审记录。实现与本文不同的地方：

- **没有 `seen` 字段**：`node` 条目版本里的 `seq` 跟随时钟，它就是最后一次发布的时间。
- **`gst unlink <destination>` 保留**，只删本机配置里的一条 link，不通知任何机器，不影响成员。
- **移除记录带 `by_name`**：被移除的机器忘掉整个网络之后，仍能说出是谁移除了它。
- **是否走 UDP 路径由 `Node` 决定**，不在路由层：中间的机器只转发。
- **每个方向一条 link**：同一方向的新 link 替换旧的；配置里到同一台机器的、不带 `admit` 的第二条 link 被删掉。
- **地址不在当前网段里的离线成员**暂时不解析、不进 WireGuard，回来后自己换地址；地址冲突时 id 较小的保留。
- 被拒时带回移除记录、本机因此可以通过时，daemon 立即重试一次，不等退避。

本文把 mesh 收敛成三层（链路、状态、路由），并在状态层上引入成员和移除。兼容性不保留：协议版本、配置版本都提升，所有机器一起升级。

## 目标

1. **概念少**：每个需求落到某一层，不自带一套传输和同步机制。现有的 `relay.open`、`net.packets` 流、推送流、记录过期、`link.remove` 都消失。
2. **成员和在线分开**：机器加入后一直是成员，离线只是状态；只有 `gst remove` 让它离开。
3. **用起来简单**：命令只有 `add` 和 `remove` 管成员，link 只是连接方式。
4. **最终一致，并且说清楚**：不用共识；每类共享状态都有一条写明的合并规则，任意两台机器连上就收敛。

非目标：控制信息走 UDP；中心服务器；对恶意成员的防护（成员之间完全信任，身份靠 SSH 授权）。

## 总览

```
┌────────────────────────────────────────────────────────────────┐
│ 应用：虚拟网络（WireGuard、DNS）、UDP 打洞、status、ping、remove   │
├────────────────────────────────────────────────────────────────┤
│ ③ 路由层  send(to, msg)：按路由表逐跳转发；请求 / 应答 / 包         │
│           路由表由状态层里的 SSH 链路图算出                         │
├────────────────────────────────────────────────────────────────┤
│ ② 状态层  全网复制的一张表：node/<id>、removed/<id>、network       │
│           只和相邻机器说话：连上时互发整张表，之后洪泛变化           │
├────────────────────────────────────────────────────────────────┤
│ ① 链路层  SSH 链路：到一台相邻机器的、有序可靠的帧管道               │
└────────────────────────────────────────────────────────────────┘
```

每层只用它下面的层：

| 层     | 接口                                                                             | 用到       | 不知道                   |
| ------ | -------------------------------------------------------------------------------- | ---------- | ------------------------ |
| ① 链路 | `Send(type, body, urgent)`、收到的帧、`Up` / `Down` 事件、对端是谁                       | SSH        | 帧里是什么、网络里还有谁 |
| ② 状态 | `Get` / `Put` / `Watch`，按条目类型合并                                          | 链路       | 消息怎么转发             |
| ③ 路由 | `Send(to, kind, payload)`、`Call(ctx, to, method, params)`、`Handle(method, fn)` | 链路、状态 | 状态怎么同步、谁是成员   |

**状态层在路由层下面**，和 OSPF 一样：先靠相邻机器之间的同步得到全网的链路图，才算得出路由表。所以同步不能经过路由，它只在一条链路的两端之间进行；路由层发的消息则可以跨多跳。链路上因此有两种帧，各归一层，链路层只按 `type` 分发，不解析内容。

UDP 路径不是链路：它不运帧，只是两台机器之间给 WireGuard 包走的捷径，见[UDP 路径](#udp-路径)。

## ① 链路层

### SSH 链路

建立方式不变（见 `mesh.md`「link 的建立」）：发起方用 `ssh -G` 解析目标，建立 SSH 连接，执行对端的 `gst peer-bridge`，接到对端 daemon 的 control socket。peer-bridge 保留：兼容性最好，并且能在对端检查 `gst up`、按需重启 daemon。

变化：

- **不再用 yamux。** 握手之后，一条链路就是一个有序的帧序列，双方都可以随时发送。
- **对端 gst 的位置固定。** `gst up` 把当前可执行文件链接到 `$HOME/.local/state/gst/bin/gst`（与平台无关）。远端命令是

  ```sh
  sh -c 'g="$HOME/.local/state/gst/bin/gst"; [ -x "$g" ] || g=gst; exec "$g" peer-bridge'
  ```

  外面包一层 `sh -c`，对端 login shell 是 fish 等也能执行。`--remote-gst` 删除。

#### 握手

SSH 连接接到对端 daemon 的 control socket 之后，两个 daemon 还互不认识。握手就是双方各发一个 `Hello`、各自检查对方的那一步；`Hello` 是握手里发的那个帧（4 字节长度 + JSON）。通过之前这条连接什么都不运，通过之后才是一条链路。

`Hello` 回答三个问题，前两个是链路层要知道的，第三个链路层只负责传：

| 问题               | 字段                               | 谁来判断                                                                          |
| ------------------ | ---------------------------------- | --------------------------------------------------------------------------------- |
| 说的是同一种话吗   | `protocol`、`software`、`role`     | 链路层。`protocol` 不同就拒绝，并用 `software` 告诉用户两边各是什么版本           |
| 你是谁             | `node`：`{"id", "name"}`           | 链路层。连到自己就拒绝；链路按对端的 id 向上报告。取代建 link 后的 `node.info`    |
| 你还是这个网络的吗 | `member`：`{"generation", "admit"}` | 应用层（成员规则）。链路层不看里面，交给 `Node` 判断，把结论放进自己的 `Hello`    |

- **`protocol`** 是整个 gst 协议的版本：帧格式、消息头、条目的格式、有哪些方法，全都算在这一个数里，任何一层的格式变了都加 1。它不属于某一层，放在握手里是因为握手是两台机器第一次接触的地方，不对就要在这里停下。每层各有一个版本号也可以，但那样要解释哪些组合能通，一个数更简单。
- **`role`** 说明这条连接是干什么的。daemon 的 control socket 有两种来客：本机的 `gst` 命令（`control`），和经 peer-bridge 进来的另一台机器的 daemon（`peer`）。两者握手之后说的东西不同，`peer` 才是链路。
- **`member`** 里的字段见[成员](#成员)：`generation` 是发送方的成员代数；`admit` 只在发起方出现，表示这条 link 来自一次 `gst add`、还没有成功握手过；拒绝时里面是 `removed`，拒绝方手里关于对方的那条移除记录。

过程（laptop 执行了 `gst add devbox`）：

```
laptop（发起方）                                devbox（接受方）
    │  ① Hello                                      │
    │ ────────────────────────────────────────────▶ │  检查 laptop：协议、是不是自己、有没有被移除
    │                                      ② Hello  │
    │ ◀──────────────────────────────────────────── │
    │  检查 devbox，同样三项                          │
    │  ③ 第一个帧（状态层的整张表）                    │
    │ ────────────────────────────────────────────▶ │  双方进入"运行"，之后只有帧
```

```json
① {"protocol": 6, "software": "gst 0.7.0+a2ffc87", "role": "peer",
   "node": {"id": "3f9c…", "name": "laptop"},
   "member": {"generation": 0, "admit": true}}

② {"protocol": 6, "software": "gst 0.7.0+a2ffc87", "role": "peer",
   "node": {"id": "8b21…", "name": "devbox"},
   "member": {"generation": 0}}
```

- **谁先发**：发起方先发，接受方看过之后再回。每一方只发一个 `Hello`，30 秒内没完成就断开。
- **接受方拒绝**：② 换成一个带 `error` 的 `Hello`，然后关闭连接：

  ```json
  {"protocol": 6, "software": "gst 0.7.0+a2ffc87", "role": "peer",
   "error": {"code": "removed", "message": "this machine was removed from the network"},
   "member": {"removed": {"key": "removed/3f9c…", "version": [0], "value": {"by": "8b21…", "at": "2026-11-10T08:00:00Z"}}}}
  ```

- **发起方拒绝**：它的 `Hello` 已经发出去了，所以改发一个 `bye` 帧（见下）说明原因，然后关闭。
- **被移除的检查**：对方的 id 有移除记录，且记录的代数不低于对方 `member` 里的 `generation`，就拒绝，并带上这条记录。被拒的一方把记录并入自己的状态，于是知道自己被移除了。

**一条连接只有三个状态，只往前走**：

| 状态   | 能收发什么       | 怎么离开                                   |
| ------ | ---------------- | ------------------------------------------ |
| 握手中 | 只有 `Hello`     | 双方的 `Hello` 都通过检查 → 运行；否则结束 |
| 运行   | 只有帧           | 出错、45 秒没收到帧、收到或发出 `bye` → 结束 |
| 结束   | 无，连接已关闭   | 不会回到前面的状态                         |

握手完成之前，链路层不向上面的层报告这条链路；结束之后重连是一条新的连接，重新握手。同一个方向上，同一台机器的新连接握手成功后，旧连接结束。

#### 帧

握手之后每帧是：

```
+----------------+-----------+-----------------+
| length: uint32 | type: u8  | body            |
+----------------+-----------+-----------------+
```

| type   | 名字  | body            | 归谁                                |
| ------ | ----- | --------------- | ----------------------------------- |
| `0x01` | sync  | JSON            | 状态层：一批条目，见[同步](#同步)   |
| `0x02` | msg   | 二进制头 + 载荷 | 路由层：一条消息，见[消息](#消息)   |
| `0x03` | alive | 空              | 链路层自己：保活                    |
| `0x04` | bye   | JSON            | 链路层自己：结束这条链路，并说明原因 |

- `length` 不超过 1 MiB。
- `type` 只用来把帧交给上面的某一层，链路层不解析 `sync` 和 `msg` 的 body。请求、应答、包都是 `msg` 帧，区分它们的是 body 里的 `kind`，那是路由层的事，见[消息](#消息)。
- **bye**：`{"error": {"code", "message"}, "member": {"removed": <移除记录>}}`，`member` 可选。一方主动结束链路之前发它：握手后发起方拒绝对方、运行中得知对方被移除、`gst down`、被新连接取代。对方立刻知道链路结束和原因，不用等 45 秒。没收到 `bye` 的断开（网络断了、进程被杀）靠保活发现。
- **保活**：一方 15 秒没发过任何帧，就发一个 `alive`；45 秒没收到任何帧，链路结束。这是握手之后**唯一的保活**，取代 yamux keepalive 和发起方的 SSH keepalive。

  - 为什么不能只靠 SSH keepalive：它只在发起方和对端 sshd 之间，对端的 daemon 看不到。网络无声断开时，对端 sshd 默认不探测客户端（`ClientAliveInterval` 默认关闭，也不该要求用户去改 sshd 配置），对端 daemon 会一直以为链路还在。条目不再过期之后这一点更要紧：突然离线的机器来不及更新自己的条目，只有还在线的那一端发现链路断了、从自己的条目里去掉，这条链路才从图里消失。
  - 为什么可以不要 SSH keepalive：`alive` 走的是 daemon → SSH → sshd → peer-bridge → 对端 daemon 整条路，比只到 sshd 的 SSH keepalive 查得更全；它同样让 NAT 上的连接保持活跃。握手之前的阶段由连接超时和 30 秒的握手时限管。
  - 代价：ssh 配置里的 `ServerAliveInterval`、`ServerAliveCountMax` 对 link 不再起作用，间隔固定为 15 秒和 45 秒。`internal/sshconn` 的 keepalive 代码删除。
  - 不测往返时间，所以不需要 ping / pong 这一对帧。

- **发送优先级**：每条链路两个发送队列，控制队列总是先发，包队列满 1024 个就丢，大量包不会拖住控制消息。进哪个队列由调用方说：接口是 `Send(type, body, urgent)`。状态层的 `sync` 和链路层自己的帧总是 `urgent`；路由层发 `msg` 时，请求和应答是 `urgent`，包不是。链路层不用为此看 body。
- 链路结束：事件交给状态层和路由层；发起方按退避重连（5 秒起，翻倍，最长 5 分钟）。**本机网络变化时退避清零**，立即重连（现在只有 UDP 路径这样做）。

## ② 状态层

### 表

全网复制一张表：键 → 条目。每个条目有类型、版本和值；**每种类型一条合并规则**，比较版本，大的胜。表写在磁盘上，不过期。

```json
{"key": "node/3f9c…", "version": [2, 1793700000000000000], "value": {…}}
```

#### `node/<id>`：一台机器

只有 `<id>` 那台机器写。完整的一条：

```json
{
  "key": "node/3f9c…",
  "version": [0, 1793700000000000000],
  "value": {
    "name": "laptop",
    "software": "gst 0.7.0+a2ffc87",
    "links": [
      { "peer": "<devbox 的 id>", "opened": true },
      { "peer": "<tablet 的 id>", "opened": false }
    ],
    "net": { "address": "10.99.3.7", "public_key": "<64 位十六进制>" },
    "seen": "2026-11-10T08:00:00Z"
  }
}
```

- `version` 是 `[generation, seq]`，不在 `value` 里。比较时先比 `generation`，相同再比 `seq`。
- **`seq`：同一台机器的哪条内容更新。** 每次内容变化（改名、链路建立或断开、换地址）加大：`seq` = max(上次 + 1, 当前 Unix 纳秒)，随状态写盘。
- **`generation`：这台机器第几次加入网络。** 一直是 0，只有被移除之后又被 `gst add` 加回来时才加 1。移除记录针对的是某一代，见下一节。它和 id 一样是这台机器的身份，存在配置文件的 `node` 里，不在状态文件里：状态文件丢了可以从邻居补回来，代数丢了，这台机器会带着旧代数被当成已移除而拒绝。
- 为什么要两个数：只有 `seq` 的话，移除记录只能写成"`seq` 不超过 N 的都作废"。被移除的机器如果还没收到消息，会继续发布 `seq` 更大的条目，于是自己又回到网络里。`generation` 只在有人执行 `gst add` 时才变，正常发布条目不会动它，所以移除压得住这一代的所有条目，不管 `seq` 多大。
- `links` 是此刻处于运行中的 SSH 链路，`opened` 表示是不是本机发起的（`gst status -v` 显示方向）。`net` 在本机还没进入虚拟网络时为空；gst IP 就是 `net.address`，不是单独的条目。
- **`seen`：这台机器发布这一条的时间**，别的机器用它显示离线成员最后一次在线的时间。在线的机器每 10 分钟重新发布一次自己的条目来更新它，所以精度是 10 分钟。这是唯一的定时发布，只用于显示：没有东西会因为它旧而过期。
- 收到自己的条目、且版本比手里的大（状态文件丢了、或旧进程发布过），就用更大的 `seq` 重新发布。

#### `removed/<id>`：一条移除记录

- 任何机器都能写（`gst remove`）。
- 版本：`[generation]`，被移除时那台机器的代数。版本相同而值不同时（两台机器同时移除它），`at` 较早的胜，再相同则 `by` 较小的胜，这样各机器留下的是同一条。
- 值：`{"by": "<执行 remove 的机器 id>", "at": "<时间，只用于显示>"}`。
- 生效规则：`node/<id>` 的 `generation` 不大于 `removed/<id>` 的版本，这台机器就不是成员；它的 `node` 条目从表里删除，也不再转发。
- 永久保存。每条几十字节；如果回收，长期离线的机器回来时会把被移除的机器带回网络。

#### `network`：网络的 subnet

- 任何机器都能写（`gst subnet`，或网络里第一台机器自动选）。
- 值：`{"subnet": "10.99.0.0/16"}`。
- 版本：`[manual, order]`：
  - `manual`：人选的为 1，自动选的为 0。人选的总是胜过自动选的。
  - 人选的：`order` = max(当前 Unix 纳秒, 见过的最大人选 order + 1)。在看到别人的选择之后再选，一定胜出，不受时钟偏差影响。
  - 自动选的：`order` = −(当前 Unix 纳秒)，更早的胜，两个网络合并时先有的网络保留它的 subnet。
  - 版本相同时，subnet 字符串较小的胜。
- 取代现在每台机器记录里的 `net.subnet` 和 `net.since`。

#### gst IP

没有单独的条目：每台机器在自己的 `node` 条目里选 `net.address`。由 id 决定，冲突时 id 较小的保留，较大的重新选。离线的成员仍然占着它的地址。

#### 整张表的样子

一张表就是一组互相独立的条目，每条都是 `{key, version, value}`。它们不合成一个大对象：合并、比较版本、同步都是一条一条做的，一条变了只传这一条。写盘时放在同一个文件里（`state.json`，在 control socket 旁边）。三台机器、其中 tablet 被移除过的网络，每台机器上的表都收敛成：

```json
{
  "entries": [
    { "key": "node/3f9c…", "version": [0, 1793700000000000000],
      "value": { "name": "laptop", "software": "gst 0.7.0+a2ffc87",
                 "links": [{ "peer": "8b21…", "opened": true }],
                 "net": { "address": "10.99.3.7", "public_key": "…" } } },

    { "key": "node/8b21…", "version": [0, 1793700000123000000],
      "value": { "name": "devbox", "software": "gst 0.7.0+a2ffc87",
                 "links": [{ "peer": "3f9c…", "opened": false }, { "peer": "c4d0…", "opened": false }],
                 "net": { "address": "10.99.8.2", "public_key": "…" } } },

    { "key": "node/c4d0…", "version": [0, 1793700000456000000],
      "value": { "name": "gateway", "software": "gst 0.7.0+a2ffc87",
                 "links": [{ "peer": "8b21…", "opened": true }],
                 "net": { "address": "10.99.1.9", "public_key": "…" } } },

    { "key": "removed/e77a…", "version": [0],
      "value": { "by": "8b21…", "at": "2026-11-10T08:00:00Z" } },

    { "key": "network", "version": [0, -1793600000000000000],
      "value": { "subnet": "10.99.0.0/16" } }
  ]
}
```

tablet（`e77a…`）没有 `node` 条目：它的代数 0 不大于移除记录的 0，条目已被删除。

### 同步

只在一条链路的两端之间进行，用 `sync` 帧，不经过路由层。原因有两个：

- 路由表是从这张表里的链路图算出来的，表还没同步时没有路由可用。
- 同步的对象本来就是"链路另一端那台机器"，不需要寻址，也不需要转发。

`sync` 帧只有一种内容：`{"entries": [...]}`，一批条目。规则只有两条，就是洪泛：

1. **链路建立时，双方把整张表发给对方**（太大时拆成多帧）。
2. **收到一条条目，按类型的规则和手里的比**：
   - 比手里的新：替换，写盘，然后发给**除了来源以外**的每个邻居；
   - 不比手里的新：丢弃，到此为止。

本机自己写的条目（改名、链路变化、`gst remove`）按第 2 条处理，只是没有来源，发给所有邻居。

这里的邻居和来源指的是机器，不是链路：两台机器之间两个方向各有一条链路时，它们仍是一个邻居，条目只经其中一条发一次，也不会从另一条发回去。

每条链路不用记任何东西：不记对方有什么，不记自己发过什么，也没有摘要。

- 传播会停：一条条目在每台机器上只有第一次到达时算"新"，只转发那一次。
- 不发回来源，所以没有回推。网络里有环时，环上会多出一两帧，对方一比就丢。
- 链路是有序可靠的，运行中发出的帧不会丢；链路断了重连，又是第 1 条，整张表重发。所以断开多久都能补齐，不靠定时器。
- 整张表不大：每台机器一条 `node` 条目，几百字节；20 台机器的表约 10 KB，重连时发一次。以后表真的大到值得省，再加摘要（先互报版本，只发对方缺的），那只是第 1 条的优化，不改第 2 条。
- 同一个连通分量内最终一致。网络分开时两边各自写，连上后按合并规则收敛，和收到的先后无关。

### 表的上限

每个 key 只有一条：新版本替换旧版本，旧的不保留。所以每台机器最多占一条 `node` 和一条 `removed`（被移除后 `node` 那条被删掉；再次被移除时，代数更大的移除记录替换原来那条）。

防止出错的机器把表撑大：表里 `node` 条目最多 1024 条，`removed` 条目最多 1024 条，单条不超过 64 KiB。收到会超出上限的条目时不合并，并写一条日志（现在是不声不响地丢掉）。

## ③ 路由层

### 消息

`msg` 帧的 body：

```
+---------+-----------+---------+----------+--------------+-----------+
| to: 16B | from: 16B | ttl: u8 | kind: u8 | id: uint32   | payload   |
+---------+-----------+---------+----------+--------------+-----------+
```

- `to`、`from`：节点 id 的 16 个原始字节。
- `ttl`：发出时 16，每转发一次减 1，到 0 丢弃。
- `kind`：`1` 请求、`2` 应答、`3` 包。
- `id`：请求和应答用它配对；包为 0。
- `payload`：请求是 `{"method", "params"}`，应答是 `{"result"}` 或 `{"error": {"code", "message"}}`，都是 JSON；包是原始的 WireGuard 包。

### 转发

每台机器对每条消息：

1. `to` 是自己：交给本机（请求进方法分发，应答交给等待的调用，包交给 WireGuard）。
2. 否则 `ttl` 减 1；为 0 则丢弃。
3. 包：`from` 是本机、并且本机有到 `to` 的 UDP 路径，就走 UDP；否则走 SSH 下一跳。
4. 请求和应答：走 SSH 下一跳。
5. 没有下一跳：包直接丢弃；请求则由这台机器给 `from` 回一个 `unreachable` 错误应答，让调用方立刻失败，不必等超时。

### UDP 路径

`internal/direct.Path` 原样保留。它是两台机器之间给包走的捷径，不是链路：

- **只运这两台机器自己的 WireGuard 包**，包在 UDP 上没有消息头：`to` 就是对端，`from` 就是发送方。不运 `sync`、请求和应答，也不替第三方转发。
- 所以**中间机器不用 UDP 转发别人的包**。收到 UDP 包的一方把它算作 UDP 对端发来的，而 WireGuard 的 endpoint 就是节点 id；替别人转发会让收的一方把回包发给转发者。要支持就得给每个 UDP 包加上 38 字节的头，降低 MTU，不值得。
- probe / answer / bye、选路、保活、空闲关闭，都不变。

**打洞由应用层做**（`internal/mesh` 的 `Node`），路由层只负责在有路径时用它：

- 触发：本机有包要发给某台机器、又没有到它的 UDP 路径时开始尝试；在路径建好之前，包照常走 SSH 链路。两端谁先有流量谁发起，也可能同时发起。
- 只有这一对机器参与：发起方用 `direct.offer` 把自己的地址发给对方，对方在应答里带回自己的地址，然后双方互相 probe。`direct.offer` 是路由层上的普通请求，中间的机器只是照常转发，不知道它是什么，也不会替这一对去打洞。
- 中间的机器和别人之间的 UDP 路径是另一回事：它自己有流量时，同样作为端点去尝试。
- 失败后的等待、本机换网络后重来（`direct.update`），都不变。

### 路由表

- 图：状态层里所有成员的 `node` 条目中的 SSH 链路。一条链路只有在两端的条目都列出对方时才算数。
- 算法：从本机出发的广度优先搜索，按跳数选最短；跳数相同时选下一跳 id 较小的，让结果稳定。
- 状态层每次变化后重新计算。

视图不一致时可能短暂绕圈，`ttl` 保证消息最终被丢弃。好处是会自愈：一条链路断了，下一条消息就按新的表走另一条路，不需要重建什么。

### 调用

```go
Call(ctx, to, method string, params, result any) error
Handle(method string, fn func(ctx, from string, params) (any, error))
```

- 调用方发请求，等配对的应答，`ctx` 决定超时（默认 10 秒）。
- **不自动重试**：要重试的调用方自己决定。所有方法都设计成幂等的，重复的请求无害。
- 不再有流：每次调用就是一个请求、一个应答。

### 方法

| 方法            | 参数          | 结果                         | 用途                    |
| --------------- | ------------- | ---------------------------- | ----------------------- |
| `ping`          | 无            | `{"id", "name", "software"}` | `gst ping` 检查控制路径 |
| `status`        | 无            | 对方 daemon 的 `Status`      | `gst status <machine>`  |
| `net.networks`  | 无            | `Networks`                   | 第一次自动选 subnet     |
| `direct.offer`  | `DirectOffer` | `DirectOffer`                | 开始找 UDP 路径         |
| `direct.update` | `DirectOffer` | 无                           | 本机换了网络            |
| `direct.trace`  | `{"node"}`    | `DirectTrace`                | `gst ping -v`           |

取消：`node.info`（并入握手和 `ping`）、`topology.sync`（变成 `sync` 帧）、`relay.open`、`net.packets`（包就是消息）、`link.remove`（见[命令](#命令)）。

## 成员

### 规则

- **成员**：表里有 `node/<id>`，且没有压过它的 `removed/<id>`。
- **在线**：本机现在有到它的路由，或有到它的 UDP 路径。
- **离线**：成员但不在线。名字照样解析，gst IP 照样占用，WireGuard 照样认识它；它一回来就能用。
- **最后一次在线的时间**取自对方 `node` 条目里的 `seen`，全网看到的一样，刚加入的机器也能看到。

### 加入：`gst add`

1. 本机保存一条带 `admit` 标记的 link，连上目标，握手时 `Hello` 带 `"admit": true`。
2. 双方握手通过，互发整张表。两个网络就此合并：表取并集，各条目按规则收敛。
3. 第一次握手成功后，`admit` 从配置里清掉，之后的重连不再带它。

`admit` 的作用是让被移除的机器回来。**代数总是由被移除的那台机器自己加**，条件是它知道了自己被移除，并且有一次人执行的 `gst add`：

| 情况                                                   | 过程                                                                                         |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 在网络里的机器上 `gst add X`，X 知道自己被移除了       | X 收到带 `admit` 的 `Hello`，把代数设为移除代数 + 1，在自己的 `Hello` 里回报，握手通过       |
| 同上，但 X 还不知道                                    | X 回报旧代数；发起方用 `bye` 带上移除记录后立即重连；X 这时知道了，按上一行处理              |
| 在被移除的 X 上 `gst add <网络里的机器>`               | 对方拒绝并带上移除记录；X 的这条 link 有 `admit`，所以把代数加到移除代数 + 1，立即重连，通过 |
| X 用旧的 link 连回来（没有 `admit`）                   | 被拒，X 按[移除](#移除gst-remove-machine)第 3 步处理，不会自己回来                           |

**移除不是吊销。** 第三行说明，被移除的机器只要还能 SSH 到网络里的某台机器，在它上面执行一次 `gst add` 就回来了。这和加入的规则一致：谁能 SSH 过去，谁就能加入。移除挡住的是它自己用旧配置连回来，以及别的机器继续把它当成员。要彻底挡住一台机器（比如丢了），得同时在各机器的 `authorized_keys` 里去掉它的公钥。

### 移除：`gst remove <machine>`

在任意一台机器上执行：

1. 写入 `removed/<id>`，版本为对方当前的 `generation`，然后同步出去。
2. 每台机器收到这条记录后：
   - 删掉自己配置里指向它的 link，断开与它的链路；
   - 把它从 WireGuard、DNS、路由表中去掉，释放它的地址。
3. 被移除的机器收到这条记录（从任意一条链路，或在握手被拒时）：
   - 删掉自己配置里所有的 link，断开所有链路；
   - 删掉表里所有其他机器的条目，只留下关于自己的移除记录，成为一个人的网络；
   - `gst status` 显示 `Removed from the network by <name> at <time>.`，并提示在网络里的机器上执行 `gst add`。
4. **移除本机**（`gst remove <本机的名字>`）就是离开网络：写入关于自己的移除记录，发给所有邻居，各发一个 `bye`，然后按第 3 步处理自己。别的机器看到的和它被别人移除一样。
5. 执行前检查：如果有机器只经由它连到本机，提示"`gateway` 只通过 `homelab` 连接网络，移除后它会离线，直到它连上别的机器"。

### 一致性场景

| 场景                                                 | 结果                                                      |
| ---------------------------------------------------- | --------------------------------------------------------- |
| 移除时 B 离线                                        | B 连上任意知情的机器，对方发来的表里有移除记录，执行第 2 步 |
| 被移除的 X 离线，回来后用自己的 link 去连 A          | A 在握手时拒绝，并带上移除记录；X 执行第 3 步             |
| B 和 X 都不知道，回来后 B 先连上 X                   | 暂时组成一个小岛；任意一方连上知情的机器后收敛            |
| B 离线期间，X 被移除又被 `add` 回来                  | B 手里 X 的代数较旧；互发表之后按代数收敛到新的           |
| 两台机器同时 `remove X`                              | 两条记录版本相同，按 `at`、`by` 留下同一条                              |
| 一台 `remove X`，另一台同时对已是成员的 X 执行 `add` | 不提升代数，移除胜；那条新 link 也被删掉                  |
| 网络分开时一边移除了 X                               | 合并后移除记录胜，另一边也移除 X                          |

## 命令

| 命令                                    | 变化                                                            |
| --------------------------------------- | --------------------------------------------------------------- |
| `gst add <destination> [-- <ssh 参数>]` | 新增，取代 `gst link`                                           |
| `gst remove <machine>`                  | 新增，在任意机器上执行                                          |
| `gst link`、`gst unlink`                | 删除                                                            |
| `--remote-gst`                          | 删除，见[SSH 链路](#ssh-链路)                                   |
| `gst status`                            | 离线的成员显示 `offline` 和最后一次在线的时间；被移除时显示原因 |
| `gst status -v`                         | 每条 link 带方向：`laptop → devbox`                             |

`gst --help` 的顺序：`up`、`add`、`status`、`ping`、`expose`、`unexpose`、`remove`、`name`、`subnet`、`ui`、`down`、`version`。

### `gst add`

| 情况                            | 结果                            | 输出                                                                   |
| ------------------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| 对方还不是成员                  | 加入网络，本机建一条到它的 link | `Added devbox to the network: 10.99.3.7, devbox.gst.`                  |
| 已是成员，本机还没有到它的 link | 新增一条 link                   | `devbox is already in the network; this machine now also links to it.` |
| 本机已有到它的 link             | 用新的目标和 ssh 参数替换       | `Changed this machine's link to devbox.`                               |
| 对方没有 `gst up`               | link 保存，之后自动连上         | 和现在一样，给出 `ssh -t` 的提示                                       |

- `--` 之后的参数原样存进配置，解析时传给 `ssh -G <参数> -- <destination>`。gst 读取的配置项和现在一样，`ProxyJump` 等仍然报错。
- link 按"本机 → 目标机器 id"区分，每个方向最多一条。目标 id 在第一次握手后写入配置；第一次连上时发现本机已有到同一台机器的另一条 link，就用新的替换旧的。

### 配置

```json
{
  "version": 6,
  "node": { "id": "…", "name": "laptop", "generation": 0 },
  "links": [
    {
      "destination": "devbox",
      "ssh_args": ["-p", "2200"],
      "target": "<devbox 的 id>"
    },
    { "destination": "admin@ssh.example.com", "target": "", "admit": true }
  ]
}
```

`target` 为空表示还没连上过；`admit` 只在 `gst add` 之后、第一次握手成功之前存在。subnet 不再在配置里，在状态层的 `network` 条目里。

## 虚拟网络

- WireGuard 的对端：所有成员中带 `net`、并且和本机在同一个 subnet 的，包括离线的。
- DNS（`127.0.0.1:15353`）：
  - 成员（包括离线的）：返回 A 记录，TTL 10 秒；
  - 不是成员：`NXDOMAIN`，附 SOA，否定缓存 5 秒；
  - 名字存在但没有该类型的记录（如 AAAA）：空应答，附同样的 SOA；
  - 虚拟网络还没起来：`SERVFAIL`；
  - socket 在 daemon 运行期间一直打开，不随虚拟网络开关。
- 包：WireGuard 的 endpoint 仍是节点 id，发送就是路由层的 `kind=3` 消息。

## 测试

- **链路**：帧编解码；优先级（包队列满时控制消息照常发出）；保活超时。
- **路由**：内存中的假链路组成的网络；转发、`ttl`、`unreachable`；链路断开后下一条消息改走别的路；中间机器不用 UDP 转发。
- **状态**：每种类型的合并规则；随机顺序、重复、分区的投递最后收敛到同一张表；不发回来源；有环时传播会停；写盘和重启。
- **成员**：remove 传到离线后回来的机器；被移除的机器被拒；`add` 让它回来；同时 remove 和 add。
- **集成**：三台机器上的 add、remove、两个方向的 link、网络分开后合并、DNS 解析离线的机器。
