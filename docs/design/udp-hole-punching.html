UDP 打洞从零讲起

从一个 UDP 包的字节开始，讲防火墙和 NAT 到底做了什么，打洞为什么能成，对端地址从哪里来，以及 gst 的直连在一个实际网络里走的是哪条路，最后讲它怎么加密、靠什么保证安全。

N 组和 M 组有几种尝试？

N×M，不是 N+M

同一个 socket 向对方每个同地址族的地址发探测，两个方向都发，而且收到探测后目标还会增加。见第 8 节。

打洞到底骗了什么？

让对方的包看起来像回包

防火墙只放行“内部先发过”的对话。两边都向外发一次，双方的防火墙都以为对方的包是回复。见第 5 节。

gst 用到打洞了吗？

用到一半

常见情况是一端可以被直接打到，另一端靠出站映射和地址学习。严格的“两边同时打”代码也支持。见第 9 节。

1 / 地基

一个 UDP 包里有什么

整件事的根在包头。网络上传的 UDP 包就是一段字节，里面和“谁发给谁”有关的只有四个字段：

有三个事实，后面每一步都靠它们：

  1. 路由器只看目的 IP。它查路由表，把包往下一跳送。它不验证源地址是真是假，也不记得这个包。
  2. 源地址是回信地址。收包的程序想回复，只能把收到的源和目的对调，再发一个包。除此之外，它没有其他途径知道该回到哪里。
  3. 私网地址在公网上没有路由。10.x、192.168.x 这些地址全世界有无数台机器在用，公网路由器遇到目的地址是它们的包，直接丢掉。
# 一来一回，四个字段对调
去  src=198.51.100.9:6000  dst=203.0.113.7:40001
回  src=203.0.113.7:40001  dst=198.51.100.9:6000
2 / socket

UDP 没有“连接”，也没有“服务端”

“两台机器分别 listen 一个 UDP server，然后相互连接对方”这个说法，方向是对的，但它来自 TCP。UDP 里没有 listen，也没有握手。

一个 UDP socket 就是向内核登记一个 IP:端口。登记之后可以做两件事：

  • 收：内核把目的地址是这个 IP:端口 的包交给你，谁发来的都收。每个包都附带它的源地址。
  • 发：你指定目的地址，内核填上源地址（就是你登记的那个）发出去。

所以两边对称：同一个 socket 既是“服务端”也是“客户端”。这一点是打洞的前提。向外发包用的端口，就是将来收包的端口，防火墙记下的正是这个端口。如果换一个 socket 发，源端口变了，之前开出来的洞也就对不上了。

“连接”这个词在 UDP 上只有一个含义：两边碰巧都在向对方的 IP:端口 发包。gst 的“直连”就是这样：两边都向对方的 IP:端口 发 WireGuard 的包，握手和加密由 WireGuard 在这些裸包里完成，丢了就丢了，重传交给里面的 TCP。

// gst：通配地址，每个地址族一个 socket，所有对端共用一个端口
udp, err := net.ListenUDP("udp4", &net.UDPAddr{Port: 15355})
3 / 防火墙

外面的包为什么进不来：状态防火墙

假设两台机器都有公网 IPv6，路由也通。如果路上什么都没有，A 发给 B，B 就直接收到了。挡住它的是路由器上的状态防火墙，家用路由器和公司出口几乎都有。

它的默认策略很简单：内部主动发出去的放行，外面主动发进来的丢掉。但只有这两条规则是上不了网的，因为你访问网站时，网站的回包也是“外面发进来的”。所以防火墙必须记住内部发起过哪些对话，这张表叫状态表（Linux 里叫 conntrack）：

# 防火墙对每个经过的包做的事
if 包从内部往外走:
    在表里记一条 (内部 IP:端口, 外部 IP:端口)，开始倒计时
    放行
else if 表里有 (包的目的, 包的源) 这一条:
    刷新倒计时
    放行           # 它认为这是回包
else:
    丢弃           # 通常不告诉发送方

注意判断回包的依据：只比较地址和端口。TCP 还有 SYN、ACK 这些标志位，防火墙可以看出谁先发起。UDP 包头里什么都没有，防火墙看不出一个包是“回复”还是“另一方主动发的”，只要四个字段对得上就放行。打洞利用的就是这一点。

UDP 也没有结束标志，所以表项只能靠超时删除。Linux 默认大约 30 秒，有来有回之后大约 2 分钟；家用路由器和运营商设备从几十秒到几分钟都有。这就是 gst 每秒探测一次在用地址的原因：一旦表项过期，后面的包就会被当成陌生来客丢掉。

4 / NAT

NAT：防火墙之外再加一层地址改写

IPv4 地址不够用，所以一个家庭或公司内部用私网地址，共用一个公网地址出门。根据上面第 3 个事实，私网地址的包回不来，所以出口设备要把包头改掉：

# 出去：NAT 改写源地址，并记一条映射
内部发出  src=10.0.0.2:5000      dst=198.51.100.9:6000
NAT 之后  src=203.0.113.7:40001  dst=198.51.100.9:6000

# 回来：NAT 查映射，改写目的地址
到达 NAT  src=198.51.100.9:6000  dst=203.0.113.7:40001
转发内部  src=198.51.100.9:6000  dst=10.0.0.2:5000

NAT 的映射表和防火墙的状态表是一回事，只多了一列“公网端口”。它同样靠超时清理，也同样会丢掉匹配不上的入站包。它是被迫丢的：包到了 203.0.113.7:40001，如果表里没有这个端口，它不知道该转给内网哪台机器。

这带来了一个新问题，也是打洞最难的部分：

A 不知道自己在公网上是谁。A 的网卡上只有 10.0.0.2，端口 40001 是 NAT 临时分配的，A 的操作系统里查不到。这个地址只有 NAT 自己和收到包的人知道。

再加一层也一样。运营商级 NAT（常用 100.64.0.0/10 地址段）是家用 NAT 外面又套一层，A 连自己路由器的外网地址都不是公网地址。

另外，IPv6 不一定没有这些事。有些机器的 IPv6 出口地址和网卡上的地址就不一样，说明路上有地址转换或代理。

5 / 打洞

打洞：让两边都先说话

现在可以说清楚了。两边的防火墙都只放行“内部先发过”的对话，那么让两边都向对方发一个包。A 的包走出 A 的防火墙时，在表里留下一条记录。这时 B 发来的包，对 A 的防火墙来说就是回包。

说“骗”不算错，但防火墙并没有被攻破。它的规则是“内部的机器想和谁说话，就放行谁”，而 A 确实想和 B 说话。打洞只是让两台机器同时表达这个意愿。

B 的探测目标

地址都是文档专用的示例地址，不是真实机器的地址。高亮的行是这一步新增的。

从模拟器里要看懂的三件事

  1. 第一个包常常被丢，但它没有白发。A 的第一个探测被 B 的防火墙丢掉，但它在 A 自己的防火墙上留下了记录，这才是它的作用。
  2. “同时”不需要精确。只要 B 的包到达时 A 的表项还没过期就行。gst 每 200 毫秒发一轮，持续最多 15 秒，所以两边的启动时间差几秒也没关系。
  3. 全程必须是同一个 socket。表项记的是具体端口。探测用 5000，WireGuard 换成 5001，就是另一个表项，洞对不上。

为什么 TCP 打洞难得多

TCP 有握手，防火墙看得懂 SYN。两边要同时发 SYN（TCP 的 simultaneous open），时序要求严格，还要让监听和连接共用一个端口，很多防火墙和 NAT 处理得也不好。UDP 什么状态都没有，反而容易。这也是 WireGuard 跑在 UDP 上对打洞很有利的原因。

6 / 地址

怎么拿到对端的实际地址

只有一个来源：收到的包的源地址。你的公网地址是 NAT 写在包头上的，所以必须有人收到你的包，再告诉你或直接用它。下面是三种情况：

来源怎么来的什么时候有用
本机网卡地址程序读自己的网卡，放进 offer，经 SSH 发给对方公网 IPv6、同一内网、或对方能路由到这个私网地址
对方的来包对方的探测到达时，recvfrom 返回的源地址。gst 用这个至少有一方能被对方打到
STUN向公网上的 STUN 服务器发包，它回复“我看到你的地址是这个”。gst 没用两边都不可达时才必须

STUN 没有什么魔法。它就是公网上一台会把源地址念给你听的机器，协议的核心只有这一件事。gst 里第二种情况相当于让对端节点兼任 STUN，而且不用把地址告诉你，直接回包就行。这就是下面这段代码：

// internal/direct/direct.go，receive()：source 就是对方在公网上的真实地址
switch packet[0] {
case kindProbe:
    s.send(kindAnswer, a.token, source) // 原路回复
    a.targets[source] = true            // 学到一个新目标
case kindAnswer:
    proved <- path{s, source}           // 这条路径被证明可用
}

为了不让无关的包混进来，探测里带 16 字节的 token。token 事先经 SSH 交换，只有 token 正确的包，来源才会被当成对端。探测包本身是明文，所以 token 只用来找路径，确认身份靠之后 WireGuard 的握手。在 里可以看到这个过程。

这个方法的边界也很清楚：学习地址的前提是对方的包能到你这里。如果两边都在 NAT 后面，谁的包也到不了谁，就谁都学不到，看 。解法是找一个两边都能到的第三方，就是 的 STUN。

7 / NAT 的类型

什么时候打不通：映射和过滤

NAT 的行为可以拆成两个独立的问题（RFC 4787 的分类），打洞能否成功就取决于这两个答案：

映射：同一个内部端口发往不同目标时，公网端口变不变？

  • 不变（Endpoint-Independent）：发给 STUN 和发给 B 都是 :40001。STUN 告诉你的地址，对 B 同样有效。
  • 每个目标都变（Address and Port-Dependent，俗称对称 NAT）：发给 STUN 是 :40001，发给 B 是 :40077。STUN 告诉你的地址对 B 没用。

过滤：入站包要满足什么才放行？

  • 来者不拒：映射存在就放行，谁发的都行。这种 NAT 不用打洞，有地址就能进。
  • 只看 IP：内部发过这个 IP 才放行，端口不限。
  • IP 和端口都看：内部发过这个 IP:端口 才放行。这就是第 3 节那张状态表，最常见的严格行为。

这也解释了为什么“两边都要发”：只要过滤不是来者不拒，对方的包就必须匹配你发过的目标。

两端组合（有 STUN 时）结果原因
映射都不变，过滤任意能打通STUN 给的地址准确，两边互发就开洞
一端对称，另一端只看 IP能打通新端口虽然猜不到，但 IP 对得上，包能进去，对方再从来包学到新端口
一端对称，另一端 IP 和端口都看打不通对称一端的新端口无法提前知道，见
两端都对称打不通两边都猜不到对方的端口

打不通时，Tailscale、WebRTC 这类系统会走中继服务器。gst 也一样，只是它的中继就是 SSH mesh，本来就在，所以失败的代价很低：继续走 SSH。

8 / gst

gst 代码里的每一步

一个端口，所有对端共用

daemon 每个地址族只开一个通配 socket，端口默认 15355，被占用时由系统分配。所有对端都走它，所以 NAT 上只有一条映射，防火墙也只需要记一个端口。探测靠 token 找到对端，WireGuard 的包靠来源 IP:端口 找到对端，只有用 token 证明过的来源才放行。

发包不选源地址，听系统路由，走 VPN 也可以，只要能通。macOS 例外：代理的 TUN 接管路由时，它用自己的 socket 重新发包，就算规则是直连，源端口也变了，对方防火墙上的洞对不上，所以 socket 绑到 TUN 下面那块真正上网的网卡。候选地址只排除 gst 自己网段里的地址，否则包会钻进它自己组成的路径。

持续选最快的路径

每一轮向所有候选地址发探测，收到 answer 就记下来回时间。第一个回 answer 的地址先用起来，之后两边各自比较：新地址至少测过 3 次，比当前的低 2 毫秒以上且低一成，才换过去，所以路径不会在相近的地址之间来回跳。每 30 秒重测一轮，两个方向可以走不同的路。换地址时不换 socket，WireGuard 也不用重新握手。

步骤代码对应的原理

为什么不用绑定具体 IP

用 * 时，回包的源地址由内核选。B 发探测到 homelab 的地址 X，homelab 可能从另一个地址 Y 回复。这个包到了 B 的防火墙，表里只有 X，会被丢掉，除非 B 也探测过 Y：防火墙已经为 Y 开了洞，回包才能进来。所以 Y 必须在 offer 里，而且排在最前面，不能被数量上限截掉：一台机器可能有十几个 IPv6 临时地址。gst 直接问系统发包会用哪个地址，放在第一位。成绩记在探测的目标 X 上，不看回包从哪个地址来。

为什么探测包不直接用 WireGuard

WireGuard 的握手有状态、有重试和超时，而且要先知道把包发到哪里，打洞时这正是不知道的。用几十字节的探测先把路径试出来，再让 WireGuard 的包走它，又快又便宜。探测的第一字节从 0x11 起，WireGuard 的包是 1 到 4，所以同一个 socket 上两者可以共存，这也是“全程同一个端口”能做到的原因。

9 / 实例

一个家庭加公司的网络

假设有四台机器：homelab 在家里，有公网 IPv6 且入站放行；laptop 和 devbox 都在 NAT 后面；gateway 和 devbox 在同一个内网。先把“打洞”拆成两件事：

  • 靠出站包开映射，让回包进来：这里的机器都在用。
  • 两边都不可达，靠同时发包互相开洞：这里用不到，只有两端都有真实地址、都开着防火墙时才需要。

能跑通的关键是有一端能被打到。下面都是 这种形状：一端能被打到，另一端主动向外发，被打到的一端从来包学到地址。

机器对谁能被打到走的路
laptop ↔ homelabhomelab 的公网 IPv6场景二
devbox ↔ homelabhomelab 的公网 IPv6场景二
devbox ↔ gateway互相能到内网地址没有 NAT 问题
laptop ↔ devbox两边都在 NAT 后，互相路由不到时谁也打不到场景三，继续走 SSH

如果 homelab 换了网络，失去公网 IPv6，它和 laptop、devbox 之间就会变成场景三：两边都在 NAT 后，又没有 STUN，直连建不起来，gst 继续走 SSH，不会断。

10 / 加密

直连怎么加密，靠什么保证安全

打洞只解决了包能到达的问题，UDP 本身没有任何保护。路上的任何设备都能读、能改、能伪造。安全要回答三个问题：对面是谁（认证）、别人能不能看（保密）、别人能不能改（完整性）。gst 的回答只有一个：WireGuard。UDP 路径自己不加密，它只运送 WireGuard 的包。

信任从 SSH 来

每台机器有一对 WireGuard 密钥，私钥只在本机的 net.json 里（权限 0600）。公钥放进 link-state 记录，经 SSH link 传遍 mesh。所以在发出第一个 UDP 包之前，双方已经知道对方的公钥。能把公钥放进这份记录的，只有已经用 SSH 登录进 mesh 的机器。

加密在端到端

WireGuard 用 Noise 协议握手：双方的长期密钥和临时密钥一起算出会话密钥，拿不出私钥就完不成握手。之后每个包用 ChaCha20-Poly1305 加密并认证，改动一个比特都会校验失败，包被直接丢弃；计数器防重放。会话密钥每两分钟左右换一次，所以录下流量、以后偷到私钥，也解不开过去的包。

WireGuard 的 endpoint 在 gst 里是 node id，不是地址。包走 UDP 还是 SSH，它都不知道，也不关心，所以切换路径不用重新握手，经 SSH 中转的机器看到的也只是密文。

各种攻击分别怎么挡

攻击结果靠什么
路上窃听只看到密文和元数据WireGuard 的 AEAD
中间人冒充任一端握手失败他没有和记录里的公钥配对的私钥
伪造探测包最多干扰这次尝试探测只找路径，身份在 WireGuard 握手时确认
伪造探测回复让路径多活一会做不到，来源地址和 token 都要对；就算做到，包也解不开路径只接受确认过的地址，WireGuard 校验每个包
录下流量，以后偷私钥解不开临时密钥带来的前向保密

挡不住什么

  • 元数据。路上的人知道这两个地址在通信、什么时候、流量多大，也能认出 WireGuard。gst 不做流量伪装。
  • 拒绝服务。能阻断 UDP 的人总能让直连失败，包回到 SSH。
  • 已移除但没收到通知的节点。link 已断时执行 gst remove，对方收不到 link.remove，如果也没收到路径关闭时的 bye，现有 UDP 路径会继续运行，最多到记录过期（20 到 30 分钟）。这段时间对方仍然能走这条路径。
