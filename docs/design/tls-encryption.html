TLS 加密从零讲起

TLS 和 SSH 用的是同一套数学工具。这份文档从哈希、密钥交换、签名讲到 TLS 1.3 的每一条握手消息，再对比 SSH，最后说明 gst 的 direct link 为什么这样用，以及能否换成“公钥经 SSH 传递”的模式。

TLS 和 SSH 公私钥有何区别？

加密方式基本相同，区别在如何信任公钥

两者都用临时密钥交换算出对称密钥，再用对称密钥加密数据。SSH 靠 known_hosts 和 authorized_keys 信任公钥，网站上的 TLS 靠 CA 证书链。

gst 怎么用？

经 SSH 传指纹，用 TLS 1.3 建立加密

每次尝试新生成一对 Ed25519 密钥，经 SSH 把证书指纹告诉对方。QUIC 握手时两端互相核对指纹。没有 CA，证书只是公钥的包装。

能用公钥模式吗？

信任模型已经是这样，加密不应这样做

公钥经 SSH 传递就是 gst 现在的做法。直接用公钥加密每条消息则不可取：太慢、也没有前向保密。第 10 节比较了全部方案。

01

要防的是什么

两台机器之间的包要穿过路由器、运营商和防火墙，这些设备都可能读取或改写它。加密协议要解决三件事：

威胁攻击者做什么对应的保证靠什么工具
窃听录下所有包，慢慢看机密性对称加密
篡改改包的内容、重放旧包完整性认证标签、包序号
冒充站在中间，假装是对方身份认证数字签名和公钥信任

第三项最容易被忽略。加密本身防不住冒充：如果你和中间人协商出了密钥，那么加密做得再好，也只是把数据安全地交给了中间人。

最常见的误解：公钥用来加密数据

很多介绍把 SSH 说成“用公钥加密”。现代 TLS 和 SSH 都不这样工作。你的 ~/.ssh/id_ed25519 从不加密任何一个字节，它只负责签名，证明“我是我”。真正的数据由一把临时算出来的对称密钥加密，连接结束后这把密钥就丢弃了。

03

哈希：数据的指纹

SHA-256 把任意长度的输入压缩成 32 字节，有两个关键性质：不可逆，看到指纹推不出原文；抗碰撞，找不到两份内容相同指纹的数据。所以比对 32 字节的指纹，就等于比对了整份数据。

内部过程：把输入切成 64 字节一块，维护 8 个 32 位整数的状态。每块做 64 轮混合，每轮用循环移位、异或和加法把这块数据搅进状态，最后的状态就是输出。这些操作反复叠加，输入改一位，每一轮的差异都会扩散，最终约一半的输出比特翻转。这叫雪崩效应。

04

对称加密：AES-GCM

双方已经有同一把密钥时，用它来加密数据。TLS 1.3 只允许 AEAD 算法，也就是加密和防篡改一起做。AES-GCM 由两部分组成。

加密：AES 生成密钥流，再做异或

AES 是一个带密钥的置换：输入 16 字节，输出看起来完全随机的 16 字节。AES-128 做 10 轮，每轮四步：查表替换每个字节（SubBytes），错开各行（ShiftRows），混合各列（MixColumns），异或轮密钥（AddRoundKey）。没有密钥就无法预测输出。

GCM 用它做计数器模式：从 nonce‖2 开始，对 nonce‖2、nonce‖3… 依次跑 AES，得到一条密钥流，再和明文异或。nonce‖1 留给下面的认证标签。

keystream = AES(key, nonce‖2) ‖ AES(key, nonce‖3) ‖ …
ciphertext = plaintext XOR keystream
plaintext  = ciphertext XOR keystream   异或两次还原，收方算同一条密钥流

这里有一条铁律：同一把密钥下 nonce 绝不能重复。重复时两段密文的异或等于两段明文的异或，加密形同虚设。TLS 和 QUIC 用包序号生成 nonce，序号只增不减，自然不重复。

防篡改：GHASH 认证标签

异或本身不防改：翻转密文的一位，明文的同一位也跟着翻转。所以 GCM 还要算一个 16 字节的标签。令 H = AES(key, 0)，把附加数据和密文按 16 字节分块，当作系数代入一个以 H 为变量的多项式，在有限域 GF(2¹²⁸) 里求值，再和 AES(key, nonce‖1) 异或。不知道密钥就算不出 H，也就伪造不了标签。

收方先验标签，失败就整包丢弃。包头这种不能加密的内容作为“附加数据”也计入标签，所以同样改不了。

试一下：真实的 AES-128-GCM

需要浏览器的 WebCrypto 才能计算。

另一个可选算法 ChaCha20-Poly1305 结构相同：ChaCha20 对 16 个 32 位字做 20 轮加法、异或、循环移位，生成密钥流；Poly1305 在模 2¹³⁰−5 下求多项式值，生成标签。它在没有 AES 硬件指令的机器上更快。

05

密钥交换：公开说话，共享秘密

对称加密的难题是：第一把密钥怎么来。Diffie-Hellman 的办法是让双方在公开信道上各说一个数，算出一个旁听者算不出的秘密。

可以想象调颜料：双方公开约定一种底色，各自偷偷加一种私有颜色，把混合结果公开交换，再加上自己的私有颜色。两边最后都得到“底色 + 甲 + 乙”。旁听者只看到混合后的颜料，而把混合颜料分离回原色很难。

数学上，“混色”换成模幂运算。正向 g^a mod p 很快；反过来已知结果求 a，叫离散对数，数字够大时算不出来。

p = 23 时窃听者把 22 种可能全试一遍就破解了。真实算法的搜索空间大约是 2²⁵²，全世界的计算机加起来也试不完。

X25519：换到椭圆曲线上

X25519 是同样的思路，只是把“乘方”换成椭圆曲线上的“点的倍乘”。曲线是 Curve25519：

y² = x³ + 486662·x² + x   (mod 2²⁵⁵ − 19)     基点 G 的 x = 9

曲线上的点可以按一条几何规则“相加”，结果还是曲线上的点。把 G 加自己 a 次得到 a·G，用倍加法只需约 255 步。反过来从 a·G 求 a 没有已知的快速算法。流程和上面的玩具完全对应：

甲：随机 a，发送 A = a·G          乙：随机 b，发送 B = b·G
甲算 a·B = a·b·G                  乙算 b·A = b·a·G     结果相同

公钥和私钥都只有 32 字节，比同等强度的传统 DH 小得多。

前向保密：临时密钥的意义

TLS 1.3 和 SSH 的 a、b 每条连接都重新随机生成，用完即销毁。这样就算攻击者录下全部流量，日后又偷走了机器上的长期密钥，也解不开过去的连接，因为算出会话密钥所需的 a、b 已经不存在。这个性质叫前向保密。

ML-KEM：防备量子计算机

足够大的量子计算机能用 Shor 算法解离散对数，X25519 会被攻破。今天录下的密文，将来可能被解开。ML-KEM（FIPS 203）基于另一类难题：带噪声的线性方程。

在普通线性方程 t = A·s 里，知道 A 和 t 用高斯消元就能解出 s。加上一点小噪声 t = A·s + e 之后，消元会把噪声放大，问题变得很难。这叫 LWE 问题，目前没有已知的量子快速算法。ML-KEM-768 用的元素是模 3329、256 次的多项式，矩阵是 3×3。

生成  甲：随机小的 s, e，公钥 t = A·s + e          发给乙 1184 字节
封装  乙：随机小的 r, e₁, e₂ 和秘密 m
      u = Aᵀ·r + e₁
      v = tᵀ·r + e₂ + 放大(m)                    发回甲 1088 字节
解封  甲：v − sᵀ·u = 放大(m) + 小噪声              四舍五入得到 m

两端再由 m 哈希出 32 字节的共享秘密。注意这里的结构和 DH 不同：乙选定秘密，用甲的公钥“封”起来发回。

ML-KEM 比 X25519 年轻得多，所以实际部署把两者一起用：X25519MLKEM768 同时做两种交换，把两个秘密拼起来作为输入。攻击者必须把两种都攻破才行。

06

签名：证明“我是我”

密钥交换本身不知道对面是谁。中间人可以分别和两边做一次交换。所以要用签名把身份绑到这次交换上：一方用私钥对内容签名，任何人用公钥验证，而没有私钥的人造不出能通过验证的签名。

Ed25519 建立在另一条曲线（与 Curve25519 等价的 Edwards 形式）上，B 是基点，L 是群的阶（约 2²⁵²）。私钥是整数 a，公钥是点 A = a·B。

签名  r = SHA-512(私钥派生的前缀 ‖ M) mod L      一次性的随机数，由消息确定
      R = r·B
      k = SHA-512(R ‖ A ‖ M) mod L
      S = r + k·a  mod L
      签名 = (R, S)                             共 64 字节

验证  算 k，检查  S·B  ==  R + k·A

验证为什么成立：把 S 展开，S·B = (r + k·a)·B = r·B + k·(a·B) = R + k·A。等式成立需要知道 a 才能造出 S，而 k 依赖 M，所以换一条消息，旧签名就失效了。r 起遮罩作用：没有它，从 S 能直接算出 a。

签名不是“用私钥加密”。这个说法只碰巧对 RSA 的教科书形式近似成立。Ed25519 这种签名算法根本不能加密任何东西，它只能证明。这一点在第 10 节会用到。

HKDF：从一个秘密得到多把密钥

共享秘密不能直接当密钥用，因为不同用途、不同方向都要各自的密钥。HKDF 建立在 HMAC 上，分两步：Extract 把不均匀的输入压成一把均匀的伪随机密钥；Expand 用不同的标签从它派生任意多把密钥。知道派生出的一把密钥，推不出其他密钥。

密钥派生的完整顺序

0 ──────────── Extract ─▶ Early Secret
                            │ derive("derived")
ECDHE+ML-KEM ─ Extract ─▶ Handshake Secret
                            ├─ "c hs traffic", H(CH..SH) ─▶ client handshake secret
                            ├─ "s hs traffic", H(CH..SH) ─▶ server handshake secret
                            │ derive("derived")
0 ──────────── Extract ─▶ Master Secret
                            ├─ "c ap traffic", H(CH..server Fin) ─▶ client app secret
                            └─ "s ap traffic", H(CH..server Fin) ─▶ server app secret

每个 secret 再 Expand 出： "quic key"  "quic iv"  "quic hp"

第一行的 Early Secret 给“用预共享密钥恢复会话”留位置。gst 关掉了会话恢复，所以这里输入是 0。

TLS 放进 QUIC 之后

普通 TLS 自己封装记录并跑在 TCP 上。QUIC（RFC 9001）只借用 TLS 的握手和密钥，握手消息放进 CRYPTO 帧，数据加密由 QUIC 逐包完成。一个 1-RTT 包长这样：

  • Initial 包不算保密。ClientHello 和 ServerHello 放在 Initial 包里，其密钥由明文的 Connection ID 和 RFC 公开的 salt 算出，任何人都能解开。所以路径上的设备能看到 ALPN gst-direct，但看不到证书，证书在握手密钥之下。
  • 长连接会换密钥。quic-go 默认每 10 万个包更新一次密钥，新密钥由旧 secret 经 HKDF 派生，旧的随即销毁。
  • 重放无效。接收方记录已处理的包序号，重放的旧包直接丢弃。
08

和 SSH 逐项对比

SSH 传输层（RFC 4253）的握手和 TLS 1.3 几乎同构。下面是用 Curve25519 时的流程：

1  双方互发版本字符串 V_C, V_S              明文
2  互发 KEXINIT I_C, I_S，列出支持的算法     明文
3  客户端发临时公钥 Q_C                      明文
4  服务器生成临时密钥，算出共享秘密 K，算
     H = hash(V_C‖V_S‖I_C‖I_S‖K_S‖Q_C‖Q_S‖K)
   发回 主机公钥 K_S、Q_S、用主机私钥对 H 的签名
5  客户端查 known_hosts 确认 K_S，算 K 和 H，验签
6  互发 NEWKEYS，密钥 = hash(K‖H‖"A".."F"‖session_id)
7  用户认证：客户端用 ~/.ssh/id_ed25519 对
   session_id 和请求内容签名，服务器查 authorized_keys 验证   已加密

第 4 步的 H 就相当于 TLS 的对话哈希，主机密钥的签名就相当于 CertificateVerify。第 7 步相当于客户端证书。对应关系如下：

会话密钥来源临时密钥交换临时密钥交换
数据加密AES-GCM、ChaCha20-Poly1305同类 AEAD，或 AES-CTR 加 HMAC
前向保密有有
抗量子交换X25519MLKEM768mlkem768x25519-sha256
服务器身份证书，由 CA 背书主机公钥，首次使用时记入 known_hosts
客户端身份可选，网站通常在应用层用密码必须，常用公钥写入 authorized_keys
长期密钥的用途只签名只签名
公钥的包装X.509 证书裸公钥
握手往返1 次多次
定位给任意应用加密一条连接远程登录，自带通道和端口转发

所以把两者对立成“TLS 加密”和“公私钥方式”并不准确：TLS 也是公私钥方式。真正的差别只有一个问题：你凭什么相信这把公钥属于对方？

CA 证书链（网站）陌生人之间，有第三方担保浏览器内置约百家 CA 的公钥。CA 用私钥为 example.com 的证书签名，浏览器顺着签名链验证到内置的根，并检查域名和有效期。
首次信任（SSH）第一次连接时人工确认第一次连接时弹出主机指纹，确认后写入 known_hosts。之后主机公钥一变就报警。用户公钥由管理员写进 authorized_keys。
带外固定（gst direct）已有一条可信通道证书指纹经已认证的 SSH 链路送到。TLS 握手时只接受这一个指纹。没有 CA，也不用人工确认。

gst 里的完整流程

direct link 的信任来自 SSH。SSH 负责递送“对方是谁”，TLS 负责在 UDP 路径上建立加密。

  VerifyPeerCertificate:  核对指纹,                    换成指纹校验
}

InsecureSkipVerify 这个名字看着吓人，它只关闭 CA 证书链和域名的检查。这里没有 CA 也没有域名，这两项本来就无法通过。VerifyPeerCertificate 仍然会运行，它比 CA 校验更严格：全世界只有一张证书能通过。

CertificateVerify 的签名校验不受这个选项影响，由 TLS 库始终执行。所以攻击者把对方的证书原样转发也没用，他没有对应的私钥。

谁能攻破什么

攻击者做法结果被什么挡住
路径上的窃听者录下全部 UDP 包失败算不出共享秘密。能看到 IP、端口、流量大小和时间
路径上的中间人替换 key_share，转发真证书失败两边对话哈希不同，CertificateVerify 验证不过
路径上的中间人用自己的证书失败指纹不符
路径上的中间人修改或重放数据包失败认证标签、包序号
事后偷走机器解开以前录下的流量失败临时密钥已销毁，磁盘上也没有存过
未来的量子计算机解开今天录下的流量失败ML-KEM 部分。指纹本来就不是秘密，SSH 记录被解开也不影响这一点
能拒绝服务的人丢弃 UDP 包可以加密防不住。gst 退回 SSH 路径，业务不中断
控制了某台 gst 节点改写经过它的 offer 中的指纹可以防不住。offer 在中继节点的进程里是明文，direct 的安全上限就是 mesh 的安全

最后一行是这个设计的信任边界。中继节点是你自己的机器，能改写 offer 的节点本来就能读写所有经过它的 SSH 中继流量，所以 direct link 没有引入新的信任对象。

direct 能用普通公私钥模式吗

“公钥走 SSH tunnel 传递，然后信息经过这个加密”可以有三种理解，答案各不相同。

理解一：公钥经 SSH 传递，用来确认身份

这就是 gst 现在的做法。证书里的核心内容只有一把 Ed25519 公钥，SSH 上传的是它的 SHA-256。传哈希和传公钥本身在安全上等价：公钥在握手时自己送来，比对哈希就知道是不是那一把。

之所以套一层证书，是因为 QUIC 强制使用 TLS，而 Go 的 crypto/tls 只认 X.509 证书。TLS 标准其实有裸公钥扩展（RFC 7250），但 Go 没有实现。这张 174 字节的证书只是个信封，没有 CA，也不带名字。

理解二：用对方公钥直接加密每条消息

这是教科书里的“公钥加密”，也是 TLS 1.2 及以前的 RSA 密钥传输模式所用的思路。TLS 1.3 把这种模式删掉了。逐条来看问题：

问题说明
算法不支持Ed25519 只能签名。要换成 RSA，或用 X25519 加对称算法拼出 ECIES，而后者已经回到密钥交换了
太慢、太小RSA-2048 OAEP 一次最多加密 190 字节，私钥运算比 AES 慢几个数量级。转发流量要切成海量小块
没有前向保密长期私钥一旦泄露，录下的全部历史流量都能解开。临时生成的 RSA 密钥能缓解，但生成 RSA 密钥本身很慢
不防篡改和重放公钥是公开的，谁都能加密一条假消息发过来。还要另加签名、序号和重放窗口

所以任何真实协议都只用公钥算法协商一把对称密钥。这条路不可取。

理解三：经 SSH 交换临时公钥，算出对称密钥，自己加密 UDP 包

这在密码学上完全可行。做法是在 direct.offer 里放一把临时 X25519 公钥，代替指纹：

offer  { addresses, token, public: A = a·G }  经 SSH
answer { addresses,        public: B = b·G }  经 SSH

两端： secret = X25519(自己的私钥, 对方的公钥)
       k_send, k_recv = HKDF(secret, token, 方向)
之后每个 UDP 包： AEAD(k, nonce = 序号, 明文)

因为 SSH 已经保证了公钥来自对方，密钥交换本身就完成了身份认证，签名和证书都可以省掉，UDP 上也不用再握手。WireGuard 就是这个思路：公钥事先通过带外渠道配置好，跑 Noise 协议算出密钥，用 ChaCha20-Poly1305 加密每个 UDP 包。

但这个方案有一个决定性的代价：QUIC 用不了了。QUIC 的规范把 TLS 1.3 写死，quic-go 的 Transport.Dial 也只接受 *tls.Config，没有换掉加密层的接口。而 gst 需要 QUIC 提供的东西：可靠重传、拥塞控制、流量控制、多路复用的流、保活。放弃它就要自己实现这些，或者在自制加密层上再跑 QUIC，等于加密两遍。

另外自制加密层还要自己处理 nonce 管理、重放窗口、密钥轮换，想抗量子还要自己把 ML-KEM 加进去。这些全是容易写出漏洞的地方，而 TLS 1.3 全都已经做好了。

方案对比

现状：指纹 + TLS公钥直接加密交换公钥 + 自制 AEAD
身份信任来源SSHSSHSSH
前向保密有无有
抗量子有无需自己加
UDP 上的握手1 RTT无无
能用 QUIC能不能不能

第三种方案省下的 1 RTT 对 gst 没有意义：direct link 在后台建立，业务先走 SSH，不等它。所以现状就是合适的选择：信任模型已经是“公钥经 SSH 传递”，TLS 只是 QUIC 要求的那部分实现。证书看起来复杂，实际只是一个信封。
